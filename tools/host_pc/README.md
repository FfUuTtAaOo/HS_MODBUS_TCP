# 六维力传感器 Modbus-TCP 上位机

配套 `Docs/modbus-tcp-protocol-v2.0.md` 与固件工程（STM32F103 + W5500）的 Python 上位机，
纯标准库实现（无需 pip 安装任何第三方包），支持 Windows / Linux / macOS。

```
tools/host_pc/
├── hs_modbus.py      协议层：寄存器表、字节序编解码、Modbus-TCP 客户端（可独立调用）
├── hs_app.py         tkinter 图形上位机（主程序）
├── hs_xlsx.py        极简 .xlsx 写出器（纯标准库，供「保存数据」用）
├── hs_simulator.py   设备模拟器：复刻真机固件行为（含其 bug），无硬件时跑通全流程
├── hs_mapscan.py     真机寄存器地图扫描器：实测可读地址白名单与块尾边界
├── test_link.py      协议层无界面联调自测
├── test_gui.py       界面 + 协议端到端自测
├── build_exe.bat     一键打包免安装 exe（Windows）
├── run_host.bat      双击启动上位机（Windows）
└── run_simulator.bat 双击启动模拟器（Windows）
```

## 1 运行环境

* Python 3.8 及以上，**必须带 tkinter**（Windows 官方安装包默认包含；
  若使用精简版/嵌入式发行版可能缺失，用 `python -c "import tkinter"` 检查）。
* 无需安装第三方依赖。

启动上位机：

```bash
cd tools/host_pc
python hs_app.py                              # 默认连接 192.168.1.12:502
python hs_app.py --host 192.168.1.100 --port 502 --order CDAB --write-order DCBA
```

不带参数时用的就是真机固件的真实字节序（`--order CDAB --write-order DCBA`），
所以**直接连真机即可，不需要先手工调字节序**。

Windows 下也可直接双击 `run_host.bat`。

### 1.1 打包成免安装 exe（Windows）

已提供打包好的单文件程序：**`dist/hs_host.exe`（约 11 MB）**。
拷到任何 Windows 机器上双击即可运行，**目标机器不需要安装 Python 或任何依赖**
（解释器、tkinter、Tcl/Tk 全部打包在内）。

首次启动会解压到临时目录，约慢 1~3 秒；个别杀毒软件对 onefile 打包的程序有误报，
如遇拦截请加白名单，或改用 `--onedir` 方式重新打包。

需要重新打包时，双击 **`build_exe.bat`** 即可（自动检查 tkinter、按需安装
PyInstaller、生成图标并打包）。若要手工执行：

```bash
python -m PyInstaller --onefile --windowed --name hs_host \
    --icon hs_host.ico --version-file version_info.py --clean --noconfirm hs_app.py
```

> **两个易踩的坑**
> 1. 打包用的 Python **必须带 tkinter**，否则打完的 exe 一启动就报
>    `ModuleNotFoundError: No module named 'tkinter'`（症状是产物明显偏小）。
>    打包日志里出现 `Including run-time hook 'pyi_rth__tkinter.py'` 才说明 Tk 打进去了。
> 2. 改了 `.py` 源码后**必须重新打包**，直接跑旧 exe 会看到「新源码的行号 +
>    旧逻辑的异常」，很容易误判。

验证打包结果（建完界面立即退出，退出码 0 即正常）：

```bash
dist\hs_host.exe --selftest
```

## 2 关于 float32 字节序（重要，请先读这一节）

协议文档 v2.0 的示例字节（`0.1 → 3D CC CC CD`、`1000.0 → 44 7A 00 00`）是**标准大端 ABCD**，
但文档正文却把 float32 标注为「小端」——**文档自相矛盾，示例才是对的**。

更麻烦的是，固件里同一份数据有**三条字节序不同的路径**：

| 路径 | 固件实现 | 线上字节序 | `1.0f` 的线上字节 |
|:--|:--|:--|:--|
| FC03 轮询读 | `mb_reg_read()`：`val = lo ? (uint16_t)u : (uint16_t)(u>>16)`，寄存器按大端上线 | **CDAB** | `00 00 3F 80` |
| FC10 写入 | `buf_to_float()`：按**小端**解释 PDU 数据字节 | **DCBA** | `00 00 80 3F` |
| 主动推流帧 | `main.c` 手工组包：`u, u>>8, u>>16, u>>24` | **DCBA** | `00 00 80 3F` |

实测真机推送帧的 24 字节数据，只有按 DCBA 解析才得到量级合理的六个值，
其余三种字节序都会给出 1e17 量级的荒谬值 —— 与上面的源码分析一致。

**上位机的处理方式**（不需要你手工试）：

* 工具栏把两条口径**分开设置**：「轮询 FC03 字节序」与「单次 / 写入 FC10 / 推流 字节序」，
  默认值分别是 `CDAB` 与 `DCBA`，即真机固件的实际行为；
* **连接时自动探测**：读阈值范围 `0x007C~0x007F`（出厂 `0.1 / 50000.0`）与过载阈值
  `0x0070~0x007B`（出厂 `2000/2000/5000/200/200/200`）作交叉判据，唯一确定轮询字节序；
* 「**读取字节序自检**」按钮：打印四种字节序的对照表并写回结论；
* 「**写入字节序自检**」按钮：写入-回读往返测试确定写入路径字节序，
  **自愈且不改动设备参数**（测完按原值写回并回读校验）。

> 若后续固件按文档统一成标准大端，把两个下拉框都切到 `ABCD` 即可，无需改代码。

### ✅ 寄存器块尾少 1 格（「非法数据地址 0x02」的根因）—— 已在固件中修复

> **2026-09-29 更新**：固件已修复（`mb_reg_read()` 两处 `case` 补 `+ 1`）。
> 本节保留，一是记录问题现场，二是说明上位机对**尚未升级的旧设备**同样兼容。

**修复前**：按协议文档写 `0x0033 × 12` / `0x007C × 24` 必然被拒（异常 `0x02`）：

| 块 | 协议文档（= 修复后） | 修复前实际可读 | 后果 |
|:--|:--|:--|:--|
| 控制 + 六维力 | `0x0030~0x003E` | `0x0030~0x003D` | 轮询读不到 Mz 高 16 位（`0x003E`） |
| 阈值范围 | `0x007C~0x0093` | `0x007C~0x0092` | Mz 最大值（`0x0093`）读不到 |

具体表现：`0x0033 × 12`、`0x007C × 24` 被拒（异常 `0x02`），
而 `0x0033 × 11`、`0x007C × 23` 正常。

**根因**（这点很容易判错，记一下）：**不是**头文件的 `MB_BLK_*_END` 写大了，
而是 `mb_reg_read()` 的两处 `case` 范围各**漏掉了最后一格**。
同文件里 Zero / Overload 两块都规规矩矩写了 `+ 1`，只有 Force / Range 两块漏了：

```c
case MB_REG_ZERO_FX ... MB_REG_ZERO_MZ + 1:         /* ✓ 12 个寄存器 */
case MB_REG_OVL_FX  ... MB_REG_OVL_MZ  + 1:         /* ✓ 12 个寄存器 */
case MB_REG_FORCE_FX ... MB_REG_TORQUE_MZ:          /* ✗ 只到 0x003D */
case MB_REG_RANGE_FX_MIN ... MB_REG_RANGE_MZ_MAX:   /* ✗ 只到 0x0092 */
```

于是整段请求通过了 `valid_range()`、却在逐字 `switch` 里于末位落到 `default`，
回异常 `0x02`。**修复方式就是补 `+ 1`，块尾宏原本是对的、不用动。**

**上位机的处理方式（新旧设备都兼容）**：连接后先实测这两个块的真实可读长度
（能力探测），再按实测长度裁剪请求；读不到的通道**显示为「—」并说明原因，
绝不编造数值**。所以：

| 对接的设备 | 力块/范围块 | Mz 表现 |
|:--|:--|:--|
| 新固件（含 P0-1 修复） | 12 / 24 | 有真值 |
| 旧固件（未升级） | 11 / 23 | 显示「—」，并在日志说明原因 |

用 `hs_mapscan.py` 可以自己复现这份实测结果（只读，无副作用）：

```bash
python hs_mapscan.py 192.168.1.12 502
```

完整的固件问题清单与修复补丁见 **`Docs/modbus-tcp-实现审查.md`**。

### 六维力数据保存（Excel）

右下角日志栏里、紧挨「保存日志」的**开始保存数据 / 停止保存数据**：

| 项 | 说明 |
|:--|:--|
| 表格式 | 真正的 `.xlsx`，可直接用 Excel / WPS 打开，无需任何第三方库 |
| 六列 | `FX` `FY` `FZ` `TX` `TY` `TZ`（**没有时间戳列**，行号即采样序号） |
| 存放位置 | **程序（`.exe`）同目录**，文件名 `hs_force_YYYYmmdd_HHMMSS.xlsx`，不用每次选路径 |
| 起止 | 点一下开始记，再点一下停止；开始时会自动补发 `0x0002` 开连续转换，停止时补发 `0x0001` |
| 实时反馈 | 按钮右侧实时显示已写入行数与文件名，停止后显示「已保存 N 行 / 耗时」 |

实现要点：

- 数据来自**主动推流帧**（`TID=0000`，按 `DCBA` 解析）。上位机的 `on_push` 回调
  在接收线程里只做入队，落盘放在界面线程的定时器里 —— 高速推流时不会因为写盘丢帧。
- 写出是**流式**的：行片段边采边追加到临时文件，内存占用恒定，采多久都不涨；
  停止时才补上 XML 尾巴打包成 zip（`.xlsx` 本质就是 zip）。
- **不编造数值**：`None` / `NaN` / `±Inf` 的格子留空；一行六个通道全无效则整行不写，
  并在日志里报出跳过行数（老固件读不到 Mz 时，其余五个通道的数据仍会保留）。

> 用别的目录：`hs_app.py --save-dir D:\data`。程序放在只读目录时也会提示改目录。
> 单独验证写出器：`python hs_xlsx.py --selftest`。

### 连续模式下推流帧的处理

写 `0x0002` 后设备按 500 Hz / 1000 Hz 主动推送 33 字节数据帧：

```
TID=0000  PID=0000  LEN=001B  UID=01  FC=03  BYTE_CNT=18  6 × float32(24B)
```

上位机的接收线程按 MBAP 长度字段对流式数据拆帧：事务号为 0 的帧判为推送帧，
直接进波形缓冲（不写报文日志以免刷屏）；事务号非 0 的帧作为请求响应，
按 TID 唤醒对应调用。因此**采集与参数读写可以同时进行**，互不干扰。

### 单次转换的返回帧（0x0003）

写 `0x0003`（单次转换）时，设备除置位单次标志外，还会**主动回送一帧**数据，
帧格式与连续推流**完全相同**（`TID=0000 / LEN=001B / FC=03 / 6×float32`），
发完自动回到停止状态。所以「单次取数」有两条路：

| 方式 | 流程 | 字节序 | 说明 |
|:-- |:-- |:-- |:-- |
| **单次返回帧** | 写 `0x0003` → 直接收一帧 | **`DCBA`** | 上位机默认走这条，Mz 也完整 |
| 轮询读 | 写 `0x0003` → 延时 ≥2ms → 读 `0x0033` | `CDAB` | 设备不推帧时的回退路径 |

上位机的「单次触发」按钮**优先用单次返回帧**：写 `0x0003` 后等设备回送的那一帧
（首次超时 0.35 s），拿到就按 `DCBA` 解析并显示，界面与日志标注「来源：单次帧 DCBA」。
若设备是**未修复的旧固件**（那一帧只发 RS485），超时后自动回退到轮询读，
标注「来源：回退轮询 0x0033 CDAB」，并把后续等待缩短到 0.1 s，免得每次单次触发都白等。
两种方式拿到的数据都会并入波形缓冲并计入帧计数。

> 通道约定：单次返回帧从**当前输出通道**发出。若此前没写过 `0x0002`/`0x0001`，
> 通道未指定，则默认从 Modbus-TCP 返回（固件 `mb_register.c` 里 `output_interface`
> 由 0 置为 2）。通过 RS485 触发的单次转换仍从 RS485 返回。

## 4 无硬件联调

先启动模拟器，再把上位机连到 `127.0.0.1`：

```bash
python hs_simulator.py                      # 默认即修复后的固件形态：读 CDAB / 单次·写·推流 DCBA、块尾 0x003E/0x0093
python hs_simulator.py --port 15020 --rate 200
python hs_simulator.py --port 15021 --legacy-blocks --legacy-single --legacy-sticky   # 完全复刻未修复的旧固件
```

模拟器默认复刻**已修复固件**的行为（块尾 `0x003E`/`0x0093` 可读、单次转换回送 TCP 帧、
**一个报文段里的多个请求全部逐个应答**，三条路径仍是三种字节序 —— 那部分按需求未改，
**单次帧归入推流口径 `DCBA`**）。

三个 `--legacy-*` 开关分别切回**未修复旧固件**的一处行为，用来验证上位机对接
未升级设备时不会误报，也用来钉住修复效果：

| 开关 | 复刻的旧行为 | 对应缺陷 |
|:--|:--|:--|
| `--legacy-blocks` | 块尾短一格，Mz 读不全 | P0-1 |
| `--legacy-single` | 单次帧只发 RS485，TCP 收不到 | P1-6 |
| `--legacy-sticky` | **一次 recv 只处理第一帧，同批其余请求被丢弃** | P0-4 |

自动化测试（建议先跑这两个，确认环境与协议都正常）：

```bash
python hs_simulator.py --port 15020                   # 另开终端
python test_link.py --port 15020     # 协议层 43 项检查（含 12b 组协议一致性 + TCP 粘包双向断言）
python test_gui.py  --port 15020     # 界面 + 协议 27 项检查

# 对接未修复旧固件形态（三个开关可分别使用）：
python hs_simulator.py --port 15021 --legacy-blocks --legacy-single --legacy-sticky
python test_link.py --port 15021 --legacy-sticky --force-regs 11 --range-regs 23 --no-single-push
```

# 对接未修复的旧固件：
python hs_simulator.py --port 15021 --legacy-blocks --legacy-single
python test_link.py --port 15021 --force-regs 11 --range-regs 23 --no-single-push
python test_gui.py  --port 15021 --legacy
```

from hs_modbus import SensorClient, ByteOrder, Format

cli = SensorClient("192.168.1.12", 502)      # 默认就是真机字节序 CDAB/DCBA/DCBA
cli.connect()

caps = cli.probe_capabilities()              # 实测可访问范围 + 轮询字节序

    print(n)

print(cli.get_sn(), cli.get_fw_version_str())
print("阈值范围 :", cli.get_ranges())         # 读不到的项是 None
print("六维数据 :", cli.get_force())          # 旧固件的 Mz 为 None（未含 P0-1 修复时）

cli.set_format(Format.N)
cli.start()                                  # 开始连续推流

import time
for _ in range(100):
    time.sleep(0.01)
    print(cli.latest_values())

cli.stop()
cli.close()
```

## 6 常见问题

**连不上设备？**
1. `ping 192.168.1.12` 确认物理链路与网段（设备默认 IP `192.168.1.12`、掩码 `255.255.255.0`）；
2. 确认上位机防火墙未拦截 **502** 端口出站；
3. 固件启动日志（UART2）会打印 `All sockets listening on port 502`，可据此确认设备已就绪；
4. 设备支持 4 路并发连接，被占满时新连接会失败。

**连上后立刻报「操作失败：设备异常 0x02 (非法数据地址)」？**
这是**固件块尾少一格**造成的（见第 2 节），**已在固件中修复**。
若你连的是**尚未升级的旧设备**，上位机会自动做能力探测、按实测长度裁剪请求，
正常情况下不会再弹这个错。若仍出现，请：
1. 在设备信息页点「读取」看是否正常；
2. 用 `python hs_mapscan.py <设备IP>` 扫出真实可读区间，对照第 2 节的表；
3. 根本解法是给设备烧入含 P0-1 修复的固件（`build/Verify/hs.hex`），
   或按审查报告把 `mb_reg_read()` 的两处 `case` 终止值各加 `+ 1`。

**连上后「读取」随机报「操作失败：等待响应超时」？**
这是**固件在「两个请求紧挨着到达」时会把后一个丢掉**造成的（缺陷编号 P0-4，
详见 `Docs/modbus-tcp-实现审查.md`），**已在固件中修复**。

判定方法：先用探针逐条读，若 12 项全 OK，说明协议本身没问题，问题只出在
「连续 / 并发请求」这条路径上：

```bash
python hs_probe.py 192.168.1.12      # 只做 FC03 读，不写设备；正常应 12/12
```

- **根本解法**：给设备烧入含 P0-4 修复的固件 —— `build/Verify/hs.hex`
  （根目录另存了副本 `hs_v1_0_fix_tcp_sticky.hex`）。
- **过渡期**：上位机已对**只读请求（FC03）**加了「超时自动重试一次」，旧固件上的
  偶发超时会变成「稍慢但成功」，日志里会出现「只读请求自动重试第 1 次」。
  写请求（FC06/FC10）不重试，避免对设备产生重复副作用。
- 避免同时用两个上位机 / 工具连同一台设备交替操作，那会人为制造并发请求。

**数值乱跳 / 量级离谱（1e17 之类）？**
字节序不对。点「读取字节序自检」重新判定，或确认两个下拉框是
「轮询 CDAB / 写入·推流 DCBA」。参见第 2 节。

**Mz 一直显示「—」？**
上位机没有编造数值：设备固件只开放到 `0x003D`，Mz 的高 16 位（`0x003E`）读不到，
拼不出完整的 float。这说明**设备跑的还是未含 P0-1 修复的旧固件**
（烧入 `build/Verify/hs.hex` 后即可读到，新固件下 Mz 有真值）。
临时也可用连续推流看 Mz —— 推流帧本身就是完整的 24 字节。

**连续采集一段时间后设备不响应了 / 要重启？**
这是固件的 **P0-2 缺陷，已在固件中修复**：`socket_connect_num[]` 在
`DISCON / TIMEOUT` 分支未清零，推流循环于是向已关闭的套接字反复发送，
而 `w5500_socket_send()` 对死连接会自旋等待（修复前最坏 2 秒/帧），
把主循环拖死 —— 表现为「卡住几秒后恢复」，反复建连后持续卡死。
**跑旧固件的设备仍需断电重启**；烧入含 P0-2 修复的固件后不再复发。
上位机侧也已尽量避免高频反复建连（长连接、连接后一次性读参数）。

**点了「停止发送」但还在刷数据？**
`0x0001` 只停止主动推流；单次触发后回送的那一帧仍会更新数值面板，属正常现象。

**「单次触发」下方显示「来源：回退轮询」？**
说明设备在 0.35 s 内没回送单次数据帧，走的是 FC03 轮询读。多数情况是设备仍在跑
**未修复的旧固件**（那一帧只发 RS485）。若此时还有通道显示「—」，则是旧固件的
Mz 高 16 位读不到。烧入修复后的固件即可两条都消失，见第 2 节与
`Docs/modbus-tcp-实现审查.md`。

**写入阈值/网络参数没有生效？**
* 阈值：写入值必须落在允许范围内（阈值的 min/max 寄存器为 `0x007C~0x0093`，
  未含 P0-1 修复的旧固件实际只到 `0x0092`），越界会被设备忽略并置 PARAM_ERR（界面会弹窗提示）；
* 网络参数：写入后**需重启传感器**才生效。

**界面卡顿？**
把波形时间窗调小（1~2 s），或取消不需要的通道勾选。500 Hz × 20 s 窗口时数据量较大。
