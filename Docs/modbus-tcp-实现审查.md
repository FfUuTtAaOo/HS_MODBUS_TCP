## 修订说明（重要）

本报告首版曾判定「MBAP 长度字段少 1」「FC06 响应多发 1 字节」，**该结论有误，特此撤回**。

复查 `Core/Src/modbus_tcp.c` 现状并**用真机实测交叉验证**：

| 位置 | 实际代码 | 结论 |
|:--|:--|:--|
| `build_echo()` LEN | `pdu_len = 2 + data_len` | ✅ 正确 |
| FC03 响应 | `build_echo(..., 1 + bytes)` + `tx[8]=bytes`，`resp_len = 7+2+bytes` | ✅ 正确 |
| FC06 响应 | `build_echo(..., rx+8, 4)`，`resp_len = 6 + pdu_len` | ✅ 正确 |
| FC10 响应 | `build_echo(..., 4)`，`resp_len = 7+1+4` | ✅ 正确 |
| 异常响应 | LEN = 3 | ✅ 正确 |

真机实测（`tools/host_pc/hs_probe.py`）也显示：`0x0005 × 8` 响应 25 字节、LEN=19，
`0x0030 × 14` 响应 39 字节、LEN=33，**长度字段与实发字节完全一致，无残留字节**。

**上一版误判的原因**：当时用 Python「复刻」固件组包逻辑时，把复刻代码写成了
`1 + data_len` / `pdu_len - 1`，然后拿复刻结果当成了固件行为——**用错误的模型验证出了错误的结论**。
教训：核对这类问题必须直接读源码 + 真机抓包，不能只靠手写复刻。

以下按**修订后**的结论重新编排。当前真正需要修的 P0 只有两项（P0-1 寄存器块尾、P0-2 推流阻塞）。

### 二、仍不符合 / 需要加固的部分

#### P1-7 FC06 响应长度取自**请求的** LEN 字段（latent）

**位置**：`Core/Src/modbus_tcp.c:91`

```c
build_echo(tx, rx_buf, fc, rx_buf + MBAP_HDR_LEN + 1, 4);   /* 只填 12 字节 */
resp_len = (uint16_t)(6 + pdu_len);                          /* ← 却按请求 LEN 决定实发长度 */
```

同文件另两个分支都是**写死**的（FC03 `7+2+bytes`、FC10 `7+1+4`），只有 FC06 跟着请求走。
按固件原式复刻验算：

| 请求 LEN | 固件实发 | 帧内 LEN | 后果 |
|:--|:--|:--|:--|
| 6（标准客户端） | 12 | 6 | ✅ 正常 |
| 7 | 13 | 6 | 多 1 字节**未初始化栈数据**，客户端读完 12 字节后错位 1 字节 |
| 30 | 36 | 6 | 多 24 字节，流错位 24 字节 |

- **实际影响**：`pymodbus`、Modbus Poll 等标准客户端的 FC06 请求 LEN 恒为 6，**不会触发**；
  但畸形/被篡改的报文会让设备把栈内存发出去，并与客户端解析器的字节流错位。
- **修法**：改为 `resp_len = MBAP_HDR_LEN + 1 + 4;`（= 12，与 FC10 分支写法统一）。
- **注意**：模拟器用的是 `len(body)+1`，**不会**复现这个 bug，所以只有真机/严格客户端才看得见。

#### P1-8 长度校验存在 `uint16` 回绕

**位置**：`Core/Src/modbus_tcp.c:49`

```c
if (rx_len < (uint16_t)(MBAP_HDR_LEN + pdu_len - 1)) return -1;
```

`pdu_len` 为 `uint16_t`，当它 ≥ `0xFFFA` 时 `7 + pdu_len - 1` 溢出 16 位后回绕成极小值，
校验形同虚设（示例：`pdu_len = 0xFFFA` → `(uint16_t)65536 = 0`，任何长度都通过）。
后半段的 addr/count 解析仍受数组边界与 `valid_range()` 保护，所以**不会越界写**，
但这层「不完整报文保护」会被绕过。

**修法**：改用 32 位比较，并顺手加上规范的 PDU 上限：

```c
if (pdu_len < 2 || pdu_len > 254) return -1;        /* UID + PDU ≤ 254 */
if ((uint32_t)rx_len < (uint32_t)MBAP_HDR_LEN + pdu_len - 1u) return -1;
```

#### P2-7 FC10 的数量上限沿用了 FC03 的 125

`valid_range()` 对读写共用一条 `count > 125` 上限，而规范里 **FC10 是 1~123**。
当前寄存器地图最大块只有 24 个寄存器，超限请求会先被 `0x02` 挡掉，**实际不可达**；
属于潜在隐患（今后若扩表会露出来）。建议按功能码传上限，或至少在注释里标明。

#### P2-8 FC10 写 float32 块不校验起始地址的 2 字节对齐

`mb_register.c:306-344` 三个 float32 块只校验 `count % 2 == 0`，不校验
`(addr - 块基址) % 2 == 0`。例如从 `0x007D` 写 2 个寄存器：请求本意是「min[0] 的高字 + max[0] 的低字」，
固件却把那 4 字节当成一个完整 float 写进 `range_min[0]` —— 语义错位但不报错。
建议对这三个块加对齐校验，不满足返回 `0x03`。

#### P2-9 FC10 未交叉校验 LEN 与 `byte_cnt`

只比对了 `byte_cnt == count*2`，没有校验 `pdu_len == 7 + byte_cnt`。
若客户端把 LEN 报大，`mb_reg_write_multi()` 会从缓冲区尾部（超出实收范围）取数写进设备参数。
与 P1-3 呼应，建议一并校验。

#### 观察项：FC > 0x7F 的帧仍会得到响应

`build_exception()` 用 `rx[7] | 0x80`，因此一个 FC=0x83（响应码范围）的报文会收到 FC=0x83 的异常帧。
规范里 FC 高位为 1 表示「这是响应」，服务器宜静默丢弃；不过多数实现也会回 `0x01`，
**属可接受偏差**，列出仅供参考，不必强行修改。

## P0 — 必须修复

### P0-1 寄存器块尾少 1 格 ★「异常 02」的根因 —— ✅ 已修复

**现象**：上位机按协议文档连接设备时，报
`操作失败：设备异常 0x02 (非法数据地址)`。

**实测**（`tools/host_pc/hs_probe.py` / `hs_mapscan.py`，真机 `192.168.1.12:502`）：

| 请求（按文档） | 真机结果 |
|:--|:--|
| `0x0033 × 12`（六维力 6×float32） | ❌ **异常 0x02** |
| `0x007C × 24`（阈值范围 12×float32） | ❌ **异常 0x02** |
| `0x0033 × 11` | ✅ 正常 |
| `0x007C × 23` | ✅ 正常 |
| `0x0005 × 8`、`0x0050 × 12`、`0x0070 × 12`、`0x0100 × 12` 等 | ✅ 正常 |

逐地址扫描得到的**真机可读白名单**：

```
0x0001~0x0003 (3)   0x0005~0x0010 (12)   0x0030~0x003D (14)
0x0050~0x005B (12)  0x0070~0x0092 (35)   0x0100~0x010B (12)
0x0200 (1)          0x0210~0x0215 (6)
```

对照源码树头文件：

| 块 | 头文件定义 | 真机实测 | 差异 |
|:--|:--|:--|:--|
| `MB_BLK_CTRL`（清零/格式/六维力） | `0x0030~0x003E` | **`0x0030~0x003D`** | 少 1 |
| `MB_BLK_OVL`（过载阈值） | `0x0070~0x007B` | `0x0070~0x007B` | 一致 |
| `MB_BLK_RANGE`（阈值范围） | `0x007C~0x0093` | **`0x007C~0x0092`** | 少 1 |

**两处「少 1」恰好都是「最后一个 float 的第二个寄存器」**：

- `MB_REG_TORQUE_MZ = 0x003D` → Mz 需要 `0x003D~0x003E`，真机只开放到 `0x003D`；
- `MB_REG_RANGE_MZ_MAX = 0x0092` → 需要 `0x0092~0x0093`，真机只开放到 `0x0092`。

**根因**：`Core/Inc/mb_register.h` 里

```c
#define MB_BLK_CTRL_END    0x003E      /* 应为 0x003E，但见下 */
#define MB_BLK_RANGE_END   0x0093
```

而 `mb_reg_read()` 的 `switch` 只覆盖到
`case MB_REG_RANGE_FX_MIN ... MB_REG_RANGE_MZ_MAX:`（终止于 `0x0092`）与
`case MB_REG_FORCE_FX ... MB_REG_TORQUE_MZ:`（终止于 `0x003D`）——
**再往后就是 `default: *exc = MB_EX_ILLEGAL_ADDR`**。

**根因（更正）**：头文件里的 `MB_BLK_CTRL_END = 0x003E` /
`MB_BLK_RANGE_END = 0x0093` 是**正确的**（与协议文档一致），
错的是 `mb_reg_read()` 的 `case` 范围各自**漏写了最后一格**。
对照同一个 switch 里 Zero / Overload 两块，它们都规规矩矩写了 `+ 1`：

```c
case MB_REG_ZERO_FX ... MB_REG_ZERO_MZ + 1:         /* ✓ 0x0050~0x005B 12 个 */
case MB_REG_OVL_FX  ... MB_REG_OVL_MZ  + 1:         /* ✓ 0x0070~0x007B 12 个 */
case MB_REG_FORCE_FX ... MB_REG_TORQUE_MZ:          /* ✗ 只到 0x003D，漏 0x003E */
case MB_REG_RANGE_FX_MIN ... MB_REG_RANGE_MZ_MAX:   /* ✗ 只到 0x0092，漏 0x0093 */
```

所以这不是「块尾宏写大了一格」，而是**读取实现漏掉了每块最后一格**。
对应的修复方向应当是补实现（下面方案 A），而不是把块尾改小。

**后果**：

- 轮询 FC03 **无法读到完整的 Mz**（只有低 16 位，凑不出 float）；
- 阈值范围里 **Mz 的最大值不可读**；
- 任何按文档写的客户端（pymodbus、Modbus Poll、本项目上位机）都会稳定报错。

**修复（已按方案 A 实施）**：两处 `case` 范围的终止值各加 `+ 1`。
由于通道索引是由地址算出来的，多出的那一格会自动落到 `ch = 5, sub = 1`
（即第 6 通道 float32 的高字）分支，无需新增 `case`：

```c
/* Core/Src/mb_register.c */
case MB_REG_FORCE_FX ... MB_REG_TORQUE_MZ + 1:          /* 0x0033~0x003E = 12 个 */
case MB_REG_RANGE_FX_MIN ... MB_REG_RANGE_MZ_MAX + 1:   /* 0x007C~0x0093 = 24 个 */
```

同时更新了 `Core/Inc/mb_register.h` 的块边界注释，明确写下规则：
「`_END` 是 **inclusive** 的末地址，必须被 `mb_reg_read()` 的对应 `case`
范围完整覆盖 —— 块尾越出 case 范围会让 `valid_range()` 放行、
却在逐字 switch 里落到 `default` 而回异常 `0x02`。」这正是本次踩坑的地方。

> **未采纳方案 B**（把块尾宏改回 `0x003D` / `0x0092`）：那会**永久失去 Mz 的轮询
> 能力**，并让固件与已发给客户的协议文档（§3.2 写的是 `0x0033~0x003E`）不一致。

**修复前后对比（模拟器复刻 + 回归实测）**：

| 请求 | 修复前 | 修复后 |
|:--|:--|:--|
| `0x0033 × 12` | ❌ 异常 0x02 | ✅ 12 个寄存器，末位 `0x003E = 0xBFA0` |
| `0x007C × 24` | ❌ 异常 0x02 | ✅ 24 个寄存器，末位 `0x0093 = 0x459C` |
| 第 6 通道 Mz（轮询 / 单次） | 「—」（读不全） | ✅ 有真值（实测 `Mz = 1.478`） |

### P0-2 推流状态下的套接字管理缺陷会让设备卡死（需断电重启）—— ✅ 已修复

**现象**：写 `0x0002` 启动连续发送后，设备最多再推 1 帧就不再响应任何请求
（连 `0x0001` 停止也不应答）；轻度时表现为「卡约 1~3 秒后恢复」，
反复建连/断连后**持续卡死，必须断电重启**。本次联调实测复现。

**根因链路**（三处配合）：

1. `Core/Src/main.c:856` 连接建立时 `socket_connect_num[i] = 1;`
2. **断开时只在「静默断开」分支清零**（`main.c:907`）：
   ```c
   if (sr != SOCK_ESTABLISHED && g_sock[i].connected) {
       g_sock[i].connected = 0;
       socket_connect_num[i] = 0;        /* ← 只有这里清 */
   }
   ```
   而 `Sn_IR_TIMEOUT` 分支（`main.c:880-888`）和「Recover closed sockets」分支
   （`main.c:911-919`）都把 `g_sock[i].connected` 置 0 后直接 `continue`/关闭套接字，
   **没有清 `socket_connect_num[i]`**。
   由于 `connected` 已被置 0，后面那个「静默断开」判断恒为假 → **该标志永远停在 1**。
3. 推流循环（`main.c:539-552`）按标志判断：
   ```c
   for (uint8_t j = 0; j < 4; j++) {
       if (socket_connect_num[j] == 1) {
           ...
           w5500_socket_send(j, mb_buf_send, 33);   /* 对已关闭的 socket 发 */
       }
   }
   ```
4. `w5500_socket_send()`（`w5500.c:308-326`）在没有 TX 空间时会自旋等待：
   ```c
   timeout = 1000;
   do {
       tx_fsr = w5500_read_word(block, Sn_TX_FSR);
       if (tx_fsr >= len) break;
       HAL_Delay(1);
   } while (--timeout);
   ```
   已关闭的 socket 读不到有效 TX 空间 → **单次调用阻塞约 1000 ms**。

**后果**：只要有 1 个残留标志，推流每次循环就阻塞约 1 秒（4 个全残留 ≈ 4 秒），
主循环几乎无法处理任何请求 —— 完全符合实测到的「卡死 / 数秒后恢复」行为。
而且因为是**推流状态下才调用**，所以只在写 `0x0002` 之后暴露。

**修复（已实施，三层防御）**：

**第一层 —— 发送条件改判成维护完整的那个标志。**
`g_sock[i].connected` 在四条断开路径上都清零了，`socket_connect_num[]`
只是它的一个不完整副本，所以数据输出路径不该再依赖后者：

```c
/* Core/Src/main.c —— 连续推流循环 & 单次返回帧循环，两处都改 */
if (g_sock[j].connected) {                  /* 原：socket_connect_num[j] == 1 */
    w5500_socket_send(j, mb_buf_send, 33);
}
```

**第二层 —— 补全 `socket_connect_num[]` 的清零，让两个标志真正同步。**

```c
/* Sn_IR_DISCON 分支（原本置 0 后 continue，跳过后续所有检查） */
g_sock[i].connected = 0;
socket_connect_num[i] = 0;                       /* ← 补 */

/* Sn_IR_TIMEOUT 分支（同样 continue） */
g_sock[i].connected = 0;
socket_connect_num[i] = 0;                       /* ← 补 */

/* Recover closed sockets 分支 */
if (g_sock[i].connected) {
    g_sock[i].connected = 0;
    socket_connect_num[i] = 0;                   /* ← 补 */
    w5500_socket_close(i);
}
```
另外在「poll fallback 检测到 ESTABLISHED」处补置 `1`（原先只有 IR 分支才置位），
并在状态机入口加注释说明这两个标志必须成对维护。至此两者完全一致。

**第三层 —— `w5500_socket_send()` 入口加连接守卫 + 收敛超时。**
这一层不依赖上层标志是否正确，从根上保证「对死连接绝不自旋」：

```c
/* Core/Src/w5500.c */
uint8_t w5500_socket_send(uint8_t sock, const uint8_t *data, uint16_t len)
{
    uint8_t block = W5500_BS_SOCK(sock);
    uint16_t tx_fsr = 0;
    ...
    /* Guard：CLOSED 状态下 Sn_TX_FSR 永远不会 ready，
     *        没有这道判断就会把下面的等待循环跑满 */
    uint8_t sr = w5500_read_byte(block, Sn_SR);
    if (sr != SOCK_ESTABLISHED && sr != SOCK_CLOSE_WAIT) {
        return 0;
    }

    /* TX 空间等待：1000 → 100 次（≈100 ms） */
    timeout = 100;
    ...
    /* SEND_OK 等待：1000 → 100 次 */
    timeout = 100;
```

修复前最坏情况：每帧、每个残留 socket 最多阻塞 2 秒（TX 空间 1 s + SEND_OK 1 s）。
修复后：正常连接只在第一轮就通过，不进入等待；异常连接最坏 200 ms 且被守卫
提前挡掉。

> 顺带把 `mb_buf_send` 的 MBAP 头（9 字节，对每个 socket 完全相同）从循环内
> 提到了循环外，并把硬编码的 `j < 4` 改为 `j < W5500_SOCK_COUNT`。

### P0-3 float32 字节序：三条路径三种口径

| 位置 | 实现 | `1.0f` 线上字节 |
|:--|:--|:--|
| 文档正文（§1.1 表格、§3.5.2） | 声称「小端 (Little-Endian)」 | `00 00 80 3F` |
| 文档示例（§1.1 `1.0 = [0x3F80, 0x0000]`、§3.4.4 响应） | 实为**大端** | `3F 80 00 00` |
| 固件 FC03 读（`mb_register.c:101-110`） | **CDAB**（低字在前，字内大端） | `00 00 3F 80` |
| 固件 FC10 写（`buf_to_float()`，`mb_register.c:14-23`） | 按**小端**解释数据字节 | 期望 `00 00 80 3F` |
| 固件主动推流（`main.c:531-538`） | **DCBA**（标准小端） | `00 00 80 3F` |

真机实测交叉验证：推流帧的 24 字节数据，只有按 DCBA 解析才得到量级合理的六个值
（其余三种字节序给出 1e17 量级荒谬值）—— 与源码分析一致。

**后果**：

1. 上位机**一套字节序设置无法同时适配**「FC03 轮询读」与「主动推流」——两者相反；
2. 读出再写回（保存/恢复零点偏移、阈值）会打乱数据，因为写路径解析方向与读路径输出方向不同；
3. 客户照文档写代码必错，照文档示例写也错。

**建议**：三处统一为文档示例的**大端 ABCD**（行业默认）——
读用 `val = hi ? (uint16_t)(u>>16) : (uint16_t)u`，
写用 `u = (hi<<16)|lo`；同时把文档 §1.1 表格里的「小端」改成「大端」。

> 过渡期：本项目上位机已把三条路径拆成独立设置
> （`--order CDAB --write-order DCBA`，推流与写入共用），接真机开箱可用，
> 并在连接时自动探测、提供两个自检按钮。详见 `tools/host_pc/README.md`。

### P0-4 「两个请求紧挨着到达 → 第二个永远不响应」★真机「读取数据都有问题」的根因 —— ✅ 已修复

**现场现象**（2026-09-29 真机 `192.168.1.12:502`）：

```
[15:33:42] 已连接 192.168.1.12:502
[15:33:43] 操作失败：等待响应超时（TID=0x0003）
[15:33:48] 操作失败：等待响应超时（TID=0x0004）
```

连得上、`ping` 正常、单发一个请求也正常，但**连续操作就会随机超时**，且越操作越糟。

**实测定位过程**（用 `tools/host_pc/` 下的临时探针，只做 FC03 读，不写寄存器）：

| 实验 | 请求方式 | 结果 |
|:--|:--|:--|
| 单个请求 + 5 s 长等待 ×10 轮 | 每次新连接 | **10/10 正常**，2~8 ms |
| 干净串行 40 个请求 | 同一连接，等响应再发下一个 | **40/40 正常**，帧帧对号 |
| **背靠背连发 10 个请求** | 一次循环不间断 `sendall` | **只回 1 个**，其余 9 个彻底消失 |
| 串行 + 前一次暴力操作残留 | — | 出现「响应迟到整整一轮」 |
| **双线程同连接并发** | 模拟「后台探测 + 用户操作」 | **精确复刻现场症状** |
| 两条独立连接并发 | 两个客户端 | 12/12 正常（多客户端本身没问题） |

**根因是三个缺陷叠加**，缺一个都还不至于这么糟：

#### ① 一次 recv 只处理第一帧（原 P1-2）

`main.c` 把整段接收缓冲交给 `modbus_tcp_process()`，而后者只解析第一帧：

```c
uint16_t n = (rx_len < sizeof(buf)) ? rx_len : sizeof(buf);
w5500_socket_recv(i, buf, n);
modbus_tcp_process(i, buf, n, mb_tcp_send_cb, NULL);   /* 只解析第一帧 */
```

TCP 是字节流；一次取回 2 个请求（24 字节）时，第 2 个**既不处理也不应答**，
直接被从缓冲里删掉。

#### ② `Sn_IR_RECV` 边沿竞态 —— 让丢失「自我持续」

旧顺序是「读数据 → 处理 → 最后清 `Sn_IR_RECV`」。而 `SOCK_RECV` 是
**只在数据落入 RX 缓冲那一刻置位一次**的瞬时事件：

```
t0  请求 A 到达，RX 缓冲 = {A}，Sn_IR_RECV = 1
t1  主循环读 Sn_IR，看到 RECV
t2  读走 A、处理、发响应
t3  请求 B 到达，RX 缓冲 = {B}，Sn_IR_RECV = 1
t4  w5500_socket_ir_clear(sock, Sn_IR_RECV)   ← B 的标志被一并抹掉
t5  下一轮主循环：Sn_IR_RECV = 0 → 不处理 B
    B 的数据躺在 RX 缓冲里，**再也没有任何事件来触发读取**
```

B 只能等**下一个**请求 C 到达、重新置位 RECV 时才被顺带取走 —— 于是
「响应迟到整整一轮」；若 C 又被①吃掉，就继续累积，表现为
**越用越糟、随机超时**。

#### ③ `w5500_socket_send()` 的 `SEND_OK` 残留标志 —— 被 P0-2 放大

P0-2 把等待 `SEND_OK` 的自旋从 1000 次收敛到 100 次（防止断线时阻塞主循环），
但**超时退出时没有清 `Sn_IR`**：

```c
while (--timeout) {
    uint8_t ir = w5500_read_byte(block, Sn_IR);
    if (ir & Sn_IR_SEND_OK) { ... return 1; }   /* 只有命中才清 */
    if (ir & Sn_IR_TIMEOUT) { ... return 0; }
    HAL_Delay(1);
}
return 0;      /* ← 超时退出，Sn_IR 原样留着 */
```

一旦某次发送因对端 ACK 慢（延迟 ACK / 窗口满）而等到超时，`SEND_OK` 就留在
`Sn_IR` 里；**下一次** `w5500_socket_send()` 的第一次读就命中这个陈旧标志、
直接 `return 1` —— 而上一次的响应其实还压在 TX 缓冲里，要等再下一次 SEND
才被一起带出去 → 又是一种「迟到一轮」。

**三处修复**

1. `Core/Src/modbus_tcp.c` / `.h` —— 新增 `modbus_tcp_process_stream()`：
   按每帧自带的 MBAP `LEN` 逐帧切分，把缓冲里**所有完整请求**都交给
   `modbus_tcp_process()`；`PID ≠ 0` 或 `LEN` 非法时丢 1 字节重新同步；
   末尾不完整帧不消费，留给下一次。
2. `Core/Src/main.c` —— 接收处理**不再依赖 `Sn_IR_RECV` 边沿，改为每轮轮询**：

   ```c
   uint8_t buf[MB_TCP_RX_BUF_SIZE];
   for (uint8_t guard = 0; guard < 4; guard++) {
       uint16_t n = w5500_socket_recv(i, buf, sizeof(buf));  /* 用返回值，不预读 RSR */
       if (n == 0) break;
       modbus_tcp_process_stream(i, buf, n, mb_tcp_send_cb, NULL);
       if (n < sizeof(buf)) break;                           /* 已读空 */
   }
   if (ir & Sn_IR_RECV) w5500_socket_ir_clear(i, Sn_IR_RECV);
   ```

   轮询天然不丢事件（代价：每轮每 socket 多 2 次 SPI 寄存器读，500 Hz 下可忽略）；
   同时改掉「先预读 `Sn_RX_RSR` 算长度、再按该长度处理」的隐患 ——
   两处读到的长度可能不同，按预读值处理会**越界读到未初始化数据**。
3. `Core/Src/w5500.c` / `.h` —— `w5500_socket_recv()` 对 `Sn_RX_RSR` **连读两次**，
   不一致时取后者；并新增 `W5500_SOCK_BUF_MAX`，把超过 RX 缓冲容量的读数
   判为寄存器撕裂值、本轮返回 0 交给下一轮（轮询模型下能自愈）。
   `w5500_socket_send()` 在发 SEND 命令**前预清** `Sn_IR_SEND_OK|Sn_IR_TIMEOUT`，
   并在等待循环超时退出后**再清一次**。

**上位机配套加固**

`hs_modbus.py::_request()` 拆成 `_request()`（含重试策略）+ `_request_once()`：
**只读请求（FC03）超时后自动重试一次**，把旧固件上的偶发超时变成「稍慢但成功」；
写请求（FC06/FC10）不重试，避免对设备产生重复副作用。重试用新事务号，
迟到的旧响应因找不到等待者而被丢弃，不会污染后续请求。

**回归**

| 配置 | 结果 |
|:--|:--|
| 协议层（已修复形态） | test_link **43/43** |
| 界面端到端 | test_gui **27/27** |
| 协议层（`--legacy-blocks --legacy-single --legacy-sticky`） | test_link **41/41** |

新增用例「TCP 粘包：一帧含 3 个请求时全部应答」为**双向断言**：修复形态要求
3 个全回（TID A001~A003、每个 33 字节、FC=0x03），`--legacy-sticky` 形态要求
只回第一个（精确复刻旧行为）—— 模拟器默认形态比固件更健壮，这正是原 P1-2
长期没被回归暴露的原因，现在把两边都钉住了。

## P1 — 规范性问题

### P1-1 主动推流帧不符合 Modbus TCP 模型

**位置**：`Core/Src/main.c:539-552`

设备在未收到请求的情况下，用 `FC=0x03` 的响应格式、`TID=0` 主动推送 33 字节数据帧
（`00 00 00 00 00 1B 01 03 18` + 24 字节）。Modbus TCP 是**严格的主从请求-响应**协议，
规范中不存在服务器主动发送的消息。

**实际影响**：

- 严格客户端收到 `TID=0` 的帧会当作未知事务丢弃（不破坏数据，但推流对它们无效）；
- 若客户端正在等待一个真实响应，该帧会插在中间，朴素实现的客户端会错位；
- 抓包工具会把设备判为「协议违规」。

**建议**：保留作为**私有扩展**，但在文档中明确标注「非标准扩展，标准客户端不支持」；
或改用私有功能码（如 `0x41`）与标准 `FC03` 响应区分开。

### P1-2 缺少 TCP 流式组帧（粘包/拆包）—— ✅ 已修复（升级为 P0-4）

**位置**：`Core/Src/main.c`（原 889-899）

```c
uint16_t rx_len = w5500_socket_recv_size(i);   /* 有多少读多少 */
w5500_socket_recv(i, buf, n);
modbus_tcp_process(i, buf, n, mb_tcp_send_cb, NULL);   /* 只当作一整帧 */
```

- **拆包**：请求被 TCP 拆成两段时，第一段因 `rx_len < 7+1` 被 `return -1` 丢弃，
  剩余字节到达后同样解析失败 → **请求丢失**，客户端超时重试；
- **粘包**：两个请求合并在一个报文段时，只处理第一个，第二个**被静默丢弃**；
- 处理函数返回后缓冲区里的剩余字节既不处理也不报错。

**这条当时被定性为 P1（规范性），理由是「模拟器比固件更健壮，现有回归无法暴露」。**
**2026-09-29 真机联调证明它实际是 P0**：上位机连接后自动探测期间用户任何一次
快速操作，都会让两个请求紧挨着到达设备，后一个被丢弃 → 界面报
「操作失败：等待响应超时」，且**该现象会自我持续**（详见表述与 P0-4）。

**已修复**：新增 `modbus_tcp_process_stream()` 按 MBAP LEN 逐帧切分处理，
并把主循环的接收处理从「边沿触发」改为「每轮轮询 RX 缓冲」。详见下文 **P0-4**。

### P1-3 请求长度校验过松

**位置**：`Core/Src/modbus_tcp.c:62`、`:80`、`:97`

| 功能码 | 现有校验 | 规范要求 |
|:--|:--|:--|
| FC03 | `pdu_len < 5` | `pdu_len != 6`（UID+FC+地址2+数量2） |
| FC06 | `pdu_len < 5` | `pdu_len != 6` |
| FC10 | `pdu_len < 7` | 还需校验 `pdu_len == 7 + byte_cnt` |

另外未校验 `pdu_len <= 254`（Modbus TCP 上限）。
FC10 的 `byte_cnt` 已校验等于 `count*2`，但没有校验它和 `pdu_len` 是否自洽，
截断报文会导致按 `count*2` 读到报文之外的数据。

### P1-4 Unit ID 未过滤，原样回显

**位置**：`Core/Src/modbus_tcp.c:22`

对任意 Unit ID 都响应。文档 §2 写「单元标识固定为 0x01」，代码实际是回显。
单机直连无影响，多设备/网关组网时会冲突。建议明确：要么过滤（只响应 `0x01` 和 `0xFF`），
要么把文档改述为「回显请求的 Unit ID」。

### P1-5 FC06 可写系统状态寄存器

**位置**：`Core/Src/mb_register.c:234-236`

```c
case MB_REG_STATUS:  g_sys.status_flags = value;  break;
```

文档 §4 标明 `0x000F` 为**只读**，固件却允许 FC06 写入，客户端可随意篡改状态字。
建议改为返回异常 `0x02`，或明确文档化为可写。

### P1-6 单次转换（`0x0003`）对 Modbus-TCP 通道无任何返回 ★已修复

**位置**：`Core/Src/main.c:807-833`（原 `send_mode == 2` 分支）

原来那条单次分支是**写死在 RS485 上**的：

```c
} else if (g_sys.send_mode == 2) {
    /* Single-shot: send one data frame then stop */
    uint8_t buf[31];
    ...
    rs485_send_raw(buf, 29);          /* ← 无条件走串口 */
    g_sys.send_mode = 0;
}
```

它完全没有看 `output_interface`。而上位机走的是 Modbus-TCP：

| 写入 | 结果 |
|:-- |:-- |
| `0x0002` 开始转换 | `send_mode = 1; output_interface = 2;` → 连续推流走 TCP ✓ |
| `0x0003` 单次转换 | `send_mode = 2;` → 数据帧发到 **RS485 串口**，TCP 客户端一个字节都收不到 ✗ |

也就是说：**协议文档 §3.1.3 承诺的「单次转换」，在 Modbus-TCP 通道上是不存在的**。
上位机只能靠「写 `0x0003` 再回读 `0x0033`」绕过，纯 Modbus 的「一次性取数」语义是缺的。

**已做的修改**（2026-09-29）：

1. `Core/Src/main.c` —— `send_mode == 2` 分支改为按 `output_interface` 分派：
   `== 2` 时向所有 `socket_connect_num[j] == 1` 的 socket 回送一帧 33 字节数据帧
   （`00 00 00 00 00 1B 01 03 18` + 6×float32 LE），`== 1` 时保持原 RS485 行为；
2. `Core/Src/mb_register.c` —— `MB_REG_SINGLE` 在 `output_interface == 0`（从未指定过通道）
   时默认置为 `2`（Modbus-TCP），使「只写 `0x0003`、不写 `0x0002`」的纯 TCP 客户端
   也能拿到回帧；**不抢占**已经激活的通道（例如正在 RS485 连续发送时）；
3. `Docs/modbus-tcp-protocol-v2.0.md` §3.1.3 —— 补充「单次返回帧」的格式与 TID 约定。

**约定的帧格式**（与连续推流帧完全一致，便于上位机复用同一套解析）：

| 段 | 值 | 说明 |
|:-- |:-- |:-- |
| TID | `00 00` | 固定 0x0000 —— 非请求应答，不参与请求/响应匹配 |
| PID | `00 00` | 协议标识 |
| LEN | `00 1B` | 27 |
| UID | `01` | 单元标识 |
| FC | `03` | 读保持寄存器响应 |
| BYTE_CNT | `18` | 24 |
| Fx~Mz | 24 字节 | 6 × float32，单位由 `0x0032` 决定，已扣零点偏移 |

> **注意**：帧的字节序沿用了连续推流那一套（`DCBA` 标准小端），而 `0x0033` 的 FC03 轮询读
> 是 `CDAB` —— 这个三口径问题属于 **P0-3**，本次未动。上位机已分别处理。

### P1-7 FC06 响应长度取自请求的 LEN 字段（latent）—— 详见「第三轮复查」

`modbus_tcp.c:91` 的 `resp_len = 6 + pdu_len` 是三个分支里唯一跟着请求走的写法，
`build_echo()` 实际只填了 12 字节 → 非标 LEN 会多发未初始化栈数据并造成流错位。
标准客户端 LEN 恒为 6，不会触发。改为 `resp_len = MBAP_HDR_LEN + 1 + 4;` 即可。

### P1-8 长度校验存在 `uint16` 回绕 —— 详见「第三轮复查」

`modbus_tcp.c:49` 的 `(uint16_t)(MBAP_HDR_LEN + pdu_len - 1)` 在 `pdu_len ≥ 0xFFFA` 时回绕，
绕过「不完整报文」保护。改用 32 位比较 + `pdu_len ≤ 254` 上限。

## P2 — 文档与实现不符

### P2-1 `0x000F` 系统状态位根本没实现

文档 §3.4.1 定义了 5 个位（EEPROM_FAIL / ADC_FAIL / CRC_ERR / OVERLOAD / PARAM_ERR），
但 `g_sys.status_flags` 在**全工程只有 4 处**（`grep -rn status_flags Core/`）：

- `sensor_types.h:33` 定义（注释还是 `BIT0 = auto-start, BIT1 = active`，与文档又不一样）；
- `mb_register.c:95` 读取（原样返回）；
- `mb_register.c:235` FC06 写入；
- `rs485_cmd.c:106-107` 经 RS485 通道回传。

**没有任何代码根据过载、参数越界或 CRC 错误去置位，也没有「读后自动清零」。**
**结论：该寄存器恒为 0（或被写入的值），文档承诺的状态监控功能不存在。**

### P2-2 `0x0010` 统计的不是 TCP 错误

文档说是「TCP 通信异常累计次数」。实际 `comm_error_cnt++` 全部出现在
`Core/Src/rs485_cmd.c`（RS485 帧解析失败，6 处），**Modbus TCP 层从不计数**
（`modbus_tcp_process` 校验失败直接 `return -1`）。
建议：在 TCP 失败分支累加，或改文档为「RS485 通信错误计数」。

### P2-3 过载阈值写入没有范围校验

文档 §3.4.4 承诺：写入值超出 `[RangeMin, RangeMax]` 时写入无效、原值不变，
并置 `PARAM_ERR`。实际 `mb_reg_write_multi` 的 OVERLOAD 分支
（`mb_register.c:302-311`）**直接赋值**，没有任何比较：

```c
g_threshold.overload[ch] = buf_to_float(data + data_off);   /* 无范围校验 */
```

同理 RANGE 分支允许把 Min 写成大于 Max。

### P2-4 协议处理里同步擦写 Flash

**位置**：`Core/Src/mb_register.c:285`（FC10 写网络参数后调用 `flash_save_zero()`）

STM32F1 的 Flash 扇区擦除可能耗时数十至数百毫秒，会**阻塞响应**导致客户端超时。
另外函数名是「保存零点」却用于保存网络参数，语义混淆。
建议置脏标记，在主循环空闲时落盘。

### P2-5 文档 FC10 请求示例的长度字段少 2

四处示例（§3.2.2、§3.4.3、§3.4.4、§3.6.1）把 FC10 请求的 LEN 写小了 2：

```
正确：LEN = UID(1) + FC(1) + 地址(2) + 数量(2) + 字节数(1) + 数据(N) = 7 + N
写 2 个寄存器（N=4） → 0x000B，文档写成 0x0009
```

固件不校验 LEN 的绝对值（只校验「收到的字节够不够」），所以「碰巧能工作」，
但客户自己的工具会按错误长度组包。

### P2-6 文档两处笔误

1. §3.4.4 示例：`50000.0` 的大端字节应为 `47 43 50 00`，文档写成 `47 43 50 0D`；
2. §1.1 数据类型表：float32 标注为「小端」，但同行的示例 `1.0 = [0x3F80, 0x0000]`
   是**大端**；`0.1 → 3D CC CC CD` 也是大端。**表头与示例自相矛盾**。

### P2-7 / P2-8 / P2-9 —— 详见「第三轮复查」

| 编号 | 问题 | 位置 |
|:--|:--|:--|
| P2-7 | FC10 数量上限沿用了 FC03 的 125（规范为 123），当前地图下不可达 | `mb_register.c:34` |
| P2-8 | FC10 写 float32 块不校验起始地址 2 字节对齐（错位写入不报错） | `mb_register.c:306-344` |
| P2-9 | FC10 未交叉校验 `pdu_len == 7 + byte_cnt`（LEN 报大时会取到缓冲区外数据） | `modbus_tcp.c:97-106` |
